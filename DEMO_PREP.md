## PART C — System design questions (be ready to defend "why")

**Q. Why is there a single `item` table shared by eMART and eDEPOT instead of each storing manufacturer/model?**
`item` is the one source of truth for `stock_number, manufacturer_name, model_number` and all
inventory fields. eMART's `emart_products` is 1:1 with `item` and holds only sales-side data
(category, warranty, price); anything needing manufacturer/model JOINs `item`. This avoids update
anomalies and keeps the schema normalized — `(manufacturer, model)` lives in exactly one place
(and is `UNIQUE`).

**Q. How do you model the product "description" (a list of attribute–value pairs that differ per product)?**
`emart_product_attributes(stock_number, attribute_name, attribute_value)` with PK
`(stock_number, attribute_name)`. A multi-valued, schema-less attribute set can't be flat columns
(every product has different attributes); this keeps it in 1NF and lets us search by any attribute.

**Q. How is compatibility modeled, and why is it directional?**
`emart_compatibility(stock_number, compatible_stock_number)` meaning "this product can *replace*
that one." The spec's relation ("can replace") is not inherently symmetric, so we store it
directionally; for symmetric pairs we insert both `(X,Y)` and `(Y,X)`. FK + a `CHECK(stock <>
compatible)` prevent self-compatibility and dangling refs.

**Q. Where do the discount / shipping / status numbers live, and why not hard-code them?**
In the `emart_rules` table (`SHIPPING_PERCENT`, `FREE_SHIPPING_THRESHOLD`, the per-tier discount
percents, `SILVER/GOLD_STATUS_THRESHOLD`). The spec explicitly says these can change at any time,
so they must be data, not code. `OrderService` reads them at checkout (`getRule`).

**Q. Walk through checkout math.**
`subtotal = Σ qty×price` (computed in SQL). `discount = subtotal × tierPercent/100`.
`shipping = 0 if (subtotal > FREE_SHIPPING_THRESHOLD OR status='NEW') else subtotal × SHIPPING_PERCENT/100`.
`total = subtotal − discount + shipping`. Tiers: NEW 10%, GOLD 10%, SILVER 5%, GREEN 0%.
(See Q7–Q10 for one example of each tier.)

**Q. How is customer status determined?**
Auto at checkout (`updateCustomerStatus`): sum the **subtotals of the last 3 orders**; > $500 → GOLD,
> $100 → SILVER, > $0 → GREEN, no orders → NEW. Thresholds come from `emart_rules`. Managers can
also override manually (B1). The sample customers start non-NEW because (per the SampleData note)
a manager set them.

**Q. Does eMART check eDEPOT inventory during checkout? (The spec literally asks this.)**
No — checkout writes a **PENDING** order and reserves nothing. Availability is checked later, at
eDEPOT `fillOrder`, which decrements `item.quantity` and throws if stock is insufficient. Trade-off:
checkout is simple/fast and never blocks on the warehouse, but an order can be placed that can't be
filled (no reservation). We chose to "check at fill time." (Demonstrable: order #3 wants 1× AA00101
but Q15 drained AA00101 to 0, so filling #3 now would fail — see the no-reservation note.)

**Q. Why a `fulfillment_status` (PENDING/FILLED) column on orders?**
It decouples the eMART sale from the eDEPOT fulfillment, lets eDEPOT pick up pending orders later,
and makes `fillOrder` idempotent — it refuses to fill anything not `PENDING`, preventing
double-decrementing inventory (Q16).

**Q. Explain the replenishment rule and your `amountToOrder`.**
Trigger (after a fill): if **≥3 items from the same manufacturer** are below their min stock, send
that manufacturer one replenishment order containing **every** item of theirs below **max** stock.
Quantity ordered per item = `max_stock − (quantity + replenishment)` so we top up to max without
double-counting stock already in transit. (Q15: HP → AA00101=2, AA00501=3, AA00601=4.)

**Q. What's the difference between `quantity` and `replenishment`?**
`quantity` = physically in the warehouse. `replenishment` = quantity in transit (promised). A
shipping **notice** adds to `replenishment` (Q17); **receiving** the shipment moves it into
`quantity` and decrements `replenishment` (Q18). Note: generating a replenishment *order* does not
itself bump `replenishment` — that only happens when the manufacturer's notice arrives.

**Q. How do you assign a stock number to a brand-new product?**
eDEPOT assigns it on first receipt. The spec format is `XXnnnnn`; the DB enforces it with
`CHECK(REGEXP_LIKE(stock_number,'^[A-Z]{2}[0-9]{5}$'))`. New items from a notice use a sequence
(`ED` + 5 digits). Existing items are matched by `(manufacturer, model)`.

**Q. How do transactions and constraints protect data integrity?**
Multi-step operations (checkout, fillOrder, receive*) run with `autoCommit=false` and commit/rollback
atomically; `SELECT ... FOR UPDATE` locks rows to prevent concurrent over-sell. Declarative CHECKs
back this up: `quantity ≥ 0`, `quantity ≤ max_stock`, `max_stock ≥ min_stock`, valid status/notice
values, positive line quantities. So even a logic bug can't persist a negative or over-max stock.

**Q. Why snapshot `price_each` on order items?**
Orders and monthly reports must reflect the price **at purchase time**. Changing the catalog price
(Q20) must not rewrite history, so each `emart_order_items` row stores its own `price_each`.

**Q. Why `MERGE` for add-to-cart and re-run?**
It's an upsert: if the (customer, stock) line exists, increment its quantity; otherwise insert it.
Avoids duplicate-key errors and a separate exists-check round trip. Re-run additionally filters the
source order by `AND o.customer_id = ?`, so you can only re-run an order you placed, and its items
land in your own cart.

**Q. Why can a customer only display / re-run their *own* orders?**
`displayOrder` and `rerunOrder` both filter `AND o.customer_id = ?` against the logged-in session, so
a guessed order ID can't be used to read or replay someone else's purchases (a privacy leak), and
re-run always targets the clicker's own cart instead of mutating the original buyer's cart. A
non-matching ID returns the ordinary "not found" message rather than revealing that the order exists.

**Q. How does the system persist across restarts (spec requirement)?**
Everything is in Oracle via JDBC — no files. The GUI holds no state; on relaunch it reads straight
from the DB. (Demo tip: they may ask you to restart mid-demo.)

**Q. How is the manager interface gated?**
`AuthService.login` returns `is_manager`; `AppFrame` only adds the Orders/eDEPOT, Shipping, and
Manager tabs when `session.manager` is true. Customers see only Products and Cart/Checkout.

## PART D — Known issues / things to verify before you walk in

1. **Manager flag mismatch (seed vs SampleData).** See §0. Decide and fix or be ready to explain.
2. **Display/Re-run Order — RESOLVED.** Moved to the customer Cart/Checkout tab (spec 2.3) and
   scoped to the logged-in customer's own orders (`AND o.customer_id = ?` in `displayOrder`/
   `rerunOrder`). A customer can no longer view or re-run another customer's order. See Q11/Q12.
3. **No inventory reservation at checkout** — you can place an unfillable order. Defensible
   ("check at fill"), but know the trade-off; the spec explicitly asks about it.
4. **Some searches lack `ORDER BY`** (`searchByCategory/Manufacturer/Model/Attribute`, compatible) →
   row order isn't guaranteed. Add `ORDER BY p.stock_number` if you want deterministic demo output.
5. **Raw-double formatting** in product/cart display (`$1630.0`, `$239.0`). Cosmetic; the values in
   this doc match the current code. If you want clean money everywhere, format with `%.2f`.
6. **New products from a notice** get an `item` row but **no `emart_products` row**, so they're in
